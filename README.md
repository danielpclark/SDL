# SDL in Rust

A **direct, pure-Rust translation of [Simple DirectMedia Layer](https://github.com/libsdl-org/SDL) 3**.

* 100% Rust. No C code, no `build.rs` compiling anything, no `bindgen`.
* The platform-independent core has **zero third-party dependencies**. The
  platform layer reaches the OS only through the pure-Rust declarations of
  [`libc`](https://crates.io/crates/libc) and
  [`windows-sys`](https://crates.io/crates/windows-sys), and loads system
  libraries (X11, Wayland, ALSA, ...) at run time as upstream does. On
  macOS it links the system frameworks upstream links and reaches
  Objective-C through the runtime's C API, declared by hand. Nothing
  links to or loads the C SDL.
* The **implementation** is translated line by line: same algorithms, same
  constants and tables, same error strings, same quirks.
* The **API** is designed as a Rust library, not a mock-up of the C one:
  `Result`-based errors, typed values, closures instead of `void *userdata`,
  owned handles with `Drop`, methods on the types they belong to. Every item
  documents the C symbol it translates (`/// Translation of SDL_GetRectUnion()`).
* Tracks upstream `SDL-3.5.0`, commit `ea7a2dabfd1ab6b0a5720568ffd207f5825e47f1`
  (2026-10-01).

> **Status: early.** Phase 1 (the foundation every other subsystem is built
> on) is complete, and so is most of the platform-independent Phase 2:
> `SDL.c`, assertions, the events core, libm, the stdlib remainder, threads,
> CPU info, IO streams, async IO, the filesystem, storage, the audio core
> (with the dummy and disk drivers), software video (surfaces, every
> blitter, RLE, rotation, YUV conversion, BMP files), the 2D renderer
> with its software, OpenGL and OpenGL ES 2.0 backends, and the joystick, gamepad and sensor front ends
> (with the virtual joystick driver). The platform backends have started:
> the Linux evdev joystick and haptic drivers (with udev), the Windows
> joystick drivers (DirectInput, XInput, RawInput, Windows.Gaming.Input)
> with the DirectInput haptic driver, and HIDAPI (hidraw and Windows HID)
> with the Xbox, PlayStation and Nintendo Switch controller drivers and
> the HIDAPI haptic driver (Logitech wheels' force feedback), and the
> Linux/Unix and Windows power, locale, URL, time, timer and filesystem
> backends. macOS is supported too: the Cocoa video driver (with OpenGL,
> OpenGL ES through ANGLE, Metal views and Vulkan through MoltenVK), the
> Metal renderer and the GPU API's Metal backend, CoreAudio, the IOKit,
> MFi (GameController) and HIDAPI controller drivers with ForceFeedback
> haptics, the CoreMedia camera driver, the Cocoa file dialogs, tray and
> notifications, and the macOS power, locale, URL and filesystem backends,
> tested on Apple Silicon and on x86-64 under Rosetta. So is Emscripten
> (`wasm32-unknown-emscripten`, in a browser page): the canvas video
> driver with its DOM events and WebGL contexts (and the OpenGL ES 2
> renderer on them), Web Audio, the Gamepad API, the browser's camera,
> and the browser's filesystem, power, locale, URL, sensor, timer and
> main-loop backends, single-threaded as upstream's default build there
> (see [Emscripten](#emscripten)). The
> remaining front ends and platform backends come next; see
> [docs/ROADMAP.md](docs/ROADMAP.md).

## Building

```sh
cargo build --release
cargo test
cargo doc --open
```

Requires Rust 1.87 or newer. There is nothing else to install.

It builds and is tested on Linux, Windows and macOS (Apple Silicon, and
x86-64 under Rosetta). On macOS the tests that need the Cocoa video driver
are programs of their own run on the main thread (`cargo test -p sdl3
--test cocoa`, `--test cocoa_shell`, `--test cocoa_metal`, and
`cargo test -p sdl3-shadercross --test metal`; a plain `cargo test` runs
them too): they show small windows, a status item and file panels for a
moment.

Emscripten (`wasm32-unknown-emscripten`) builds and is tested too, under
node and in headless Chrome: see [below](#emscripten).

iOS (`aarch64-apple-ios`, `aarch64-apple-ios-sim`, `x86_64-apple-ios`)
builds, and on a Mac with Xcode the tests run on the iOS Simulator, through
`tools/ios_run.py` (`.cargo/config.toml`'s runner, which also boots the
simulator); of the UIKit backends power, URLs, the file system's, the
form factor, `run_app()` and the main callbacks are translated, and of the
UIKit video driver its app delegate, the application's lifecycle events,
the event pump, the displays with their modes and the windows (with
`Window::set_ios_animation_callback()`) and their input (touches, the
pointer, the Apple Pencil, the keyboard and text input), the clipboard,
message boxes, Metal views (with the Metal renderer) and OpenGL ES
contexts (EAGL, with the OpenGL ES 2 renderer), CoreAudio with the
app's audio session, and the MFi joystick and CoreMotion sensor drivers,
not yet the windows' Vulkan views:

```sh
rustup target add aarch64-apple-ios-sim
cargo test --workspace --target aarch64-apple-ios-sim
```

See "iOS Simulator" in [docs/HARDWARE_TESTING.md](docs/HARDWARE_TESTING.md).

Tests of the platform backends that need something from the system (an X
server, a PipeWire server, a GPU, a camera, a macOS window server session)
skip with a note when it's missing; [docs/HARDWARE_TESTING.md](docs/HARDWARE_TESTING.md) lists what
each one needs, how to make a missing piece fail the run
(`SDL3_TEST_REQUIRE`), and the hardware checks run with
`cargo test -- --ignored`.

### Emscripten

The workspace builds for `wasm32-unknown-emscripten` configured as
upstream's Emscripten build is: single-threaded (its default), with the
dummy process, haptic, dialog, tray and notification backends, the OpenGL
ES 2 and software renderers, and SDL_net's stub library. Checking and
linting need only the target; linking needs emsdk (CI pins 6.0.13, the
version the tests were made with):

```sh
rustup target add wasm32-unknown-emscripten
cargo check --target wasm32-unknown-emscripten    # no emcc needed
git clone https://github.com/emscripten-core/emsdk && cd emsdk
./emsdk install 6.0.13 && ./emsdk activate 6.0.13 && . ./emsdk_env.sh
```

What works there, each the browser's API as upstream's backend uses it:

* video: the canvas driver (windows on `<canvas>` elements, pixel density,
  fill-document, fullscreen, the window framebuffer, CSS and color
  cursors, pointer lock, the system theme, message boxes as `alert()`),
  the page's keyboard, mouse, touch, pen, wheel, focus, visibility,
  orientation and drag-and-drop events, and WebGL contexts (OpenGL ES 2.0
  as WebGL 1, 3.0 as WebGL 2), which the OpenGL ES 2 renderer draws with;
* audio: Web Audio (playback through a `ScriptProcessorNode`, recording
  from the microphone), and the dummy driver;
* joysticks: the Gamepad API (with rumble), and virtual joysticks;
* the camera (`getUserMedia()`, its frames read back through a canvas);
* the filesystem paths (base path `/`, pref paths under `/libsdl/`, `$HOME`)
  in emscripten's file system, which is in memory (MEMFS) unless the
  application mounts something else; `run_app()` mounts IndexedDB storage
  there with the `emscripten-persistent-path` feature;
* power (the Battery Status API), locale (`navigator.languages`),
  `open_url()` (`window.open()`), and an accelerometer and a gyroscope
  (`devicemotion` events);
* the timers and the main callbacks, on the browser's event loop, and
  `run_app()`'s `SDL_*` hints from the page's URL;
* the satellites: SDL_image (taking the browser's decoding of a preloaded
  file first, as upstream's), SDL_ttf, SDL_mixer with its decoders,
  SDL_rtf, SDL_shadercross's SPIR-V translation and the test library.

As in a browser page, nothing blocks: the main callbacks
(`sdl3::app::enter_app_main_callbacks()`, which returns at once) and the
timers run from the browser's event loop once `main` has returned, and
the main loop's end ends the program. The JavaScript SDL needs there
(upstream's `EM_JS`/`EM_ASM` blocks, the `html5.h` API) is written in Rust
too, with no `.js` file, in the internal `sdl3-emscripten` crate (its
`em_js!` and `em_asm!` macros do what clang's do).

What doesn't, as in upstream's build: threads (creating one fails,
mutexes don't lock, semaphores and conditions don't wait; so the disk
audio driver, whose devices need a thread, can't open them), processes,
Vulkan, the GPU API and the renderers on them, HIDAPI, haptics, file
dialogs, the tray, notifications and networking (SDL_net is its stub
library there: every call fails as unsupported). `SharedObject::load()`
(`dlopen()`) loads only in a program linked with `-sMAIN_MODULE`.

An application passes its own link options (Cargo gives a library's to no
one), in its `.cargo/config.toml` as this repository does for its test
programs:

```toml
[target.wasm32-unknown-emscripten]
rustflags = [
    # memory that grows past the 16 MB default
    "-Clink-arg=-sALLOW_MEMORY_GROWTH=1",
    # a larger stack (emscripten's default is 64 KB)
    "-Clink-arg=-sSTACK_SIZE=8MB",
    # OpenGL ES 3.0 contexts as WebGL 2 (without it, as with upstream's C,
    # an OpenGL ES 3.0 context is WebGL 1, OpenGL ES 2.0)
    "-Clink-arg=-sMAX_WEBGL_VERSION=2",
    # rustc passes -sWASM_BIGINT, which emcc warns is deprecated
    "-Clink-arg=-Wno-deprecated",
]
```

The test programs also have `-sMAXIMUM_MEMORY=4GB`, `-sEXIT_RUNTIME=1` (the
exit status passed on) and `-sNODE_HOST_ENV=1` (node's environment seen by
`getenv()`). Other options, as an application needs them:
`-sASYNCIFY` or `-sJSPI`, with which `delay()` (and so `wait_timeout()`)
sleeps with `emscripten_sleep()`, back in the browser's event loop, the
message boxes are a `<dialog>` they wait on, and window surface updates
and buffer swaps give the browser its turn (without, `delay()` waits
busily and a message box is an `alert()`, as upstream's; the
`SDL_HINT_EMSCRIPTEN_ASYNCIFY` hint false does the same). With Asyncify,
raise its data stack: the 4 KB default is too small for the message box
(`-sASYNCIFY_STACK_SIZE=65536`); and since Rust unwinds with WebAssembly
exceptions, which Asyncify doesn't fully support (emcc warns), nothing
may sleep while a panic unwinds (in a `Drop`). With JSPI (Chrome 137 and
later; not node 22) only `main` can sleep: in the main callbacks, timers
and event handlers a sleep throws a `SuspendError`, as upstream's does,
so turn the hint off there. `-sMAIN_MODULE`, for `dlopen()`; and
`--preload-file` with `--use-preload-plugins`, which put files in the
program's file system with the images among them decoded by the browser,
which `sdl3_image::load()` takes. The OpenGL ES 2 renderer and OpenGL ES
2.0 contexts need nothing: emscripten links its WebGL library into every
program, with `emscripten_webgl_get_proc_address()`
(`-sGL_ENABLE_GET_PROC_ADDRESS`, on by default), and the renderer passes
its vertices in buffer objects, so `-sFULL_ES2` (client-side arrays) isn't
needed. The persistent storage links emscripten's IndexedDB library
(`-lidbfs.js`) itself.

The tests run through `tools/emscripten_run.py` (`.cargo/config.toml`'s
runner; Python 3 and node 22 or newer): under node by default, and in
headless Chrome or Chromium (`CHROME`, or found in `PATH`) for the
programs that ask for a browser, or for any program with
`SDL3_EMSCRIPTEN_BROWSER=1` (`0` keeps them under node). The browser
programs (`sdl3/tests/emscripten_browser.rs`, `emscripten_video.rs`,
`emscripten_events.rs`, `emscripten_gl.rs`, `emscripten_audio.rs`,
`emscripten_joystick.rs`, `emscripten_camera.rs`, the Asyncify and
JSPI builds' `emscripten_asyncify.rs` and `emscripten_jspi.rs`, the
IndexedDB storage's `emscripten_persistent_path.rs`, and
`sdl3-image/tests/emscripten_preload.rs`) check each backend against
upstream's C run on the same page. (Cargo has no link options per test
program: the linker in `.cargo/config.toml`, `tools/emscripten_link.py`,
runs emcc with the options a program asks for in a custom section
`sdl3_link`, as the Asyncify and JSPI programs do.)

```sh
CARGO_PROFILE_DEV_OPT_LEVEL=1 cargo test --workspace --target wasm32-unknown-emscripten
SDL3_EMSCRIPTEN_BROWSER=1 SDL3_TEST_REQUIRE=browser,webgl,webaudio CHROME=/path/to/chrome \
  cargo test -p sdl3 --target wasm32-unknown-emscripten --test emscripten_browser \
  --test emscripten_video --test emscripten_events --test emscripten_gl \
  --test emscripten_audio --test emscripten_joystick --test emscripten_camera \
  --test emscripten_asyncify --test emscripten_jspi
SDL_EMSCRIPTEN_PERSISTENT_PATH=/persistent SDL3_EMSCRIPTEN_BROWSER=1 CHROME=/path/to/chrome \
  cargo test -p sdl3 --target wasm32-unknown-emscripten \
  --features emscripten-persistent-path --test emscripten_persistent_path
```

See "Emscripten" in [docs/HARDWARE_TESTING.md](docs/HARDWARE_TESTING.md)
for what is ignored under node and what each browser program checks. Not
done yet: a build with threads (emscripten's pthreads, which need the
standard library built with atomics); see
[docs/ROADMAP.md](docs/ROADMAP.md).

## Using it

```rust
use std::time::Duration;
use sdl3::video::pixels::{Color, Palette, PixelFormat};
use sdl3::video::rect::Rect;
use sdl3::{hints, log, timer};

// Geometry: methods, Option/Result instead of out-parameters.
let a = Rect::new(0, 0, 10, 10);
let b = Rect::new(5, 5, 10, 10);
assert_eq!(a.intersection(&b), Some(Rect::new(5, 5, 5, 5)));

// Pixel formats: typed, with the C constants' names and values.
let fmt = PixelFormat::ARGB8888.details()?;
assert_eq!(fmt.map_rgba(None, Color::new(0x11, 0x22, 0x33, 0x44))?, 0x44112233);
let mut pal = Palette::new(256)?;
pal.dither();

// Hints, logging: closures and RAII tokens instead of callbacks + userdata.
hints::set(hints::LOGGING, "video=debug")?;
let _watch = hints::watch(hints::VIDEO_DRIVER, |change| {
    println!("video driver hint is now {:?}", change.new_value);
})?;
log::debug!(log::Category::Video, "hello {}", "world");

// Timers: a handle that cancels on drop (or `.detach()` to keep it running).
let timer = timer::Timer::new(Duration::from_millis(16), |interval| Some(interval))?;
timer::delay(Duration::from_millis(50));
drop(timer);
# Ok::<(), sdl3::Error>(())
```

[docs/TRANSLATION_GUIDE.md](docs/TRANSLATION_GUIDE.md) lists how each C
construct maps to Rust.
